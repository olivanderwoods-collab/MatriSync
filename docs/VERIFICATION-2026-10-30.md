# MatriSync verification — 30 October 2026

This continuation adds facility credential review and exact-version doctor approval in the controlled local test-account build. It follows the approved submission core and does not reopen public facility verification. It is an intermediate development milestone, not the finished referral journey or a final-product handoff.

## Working behavior

- Explicit operator enrollment fixes the test facility approver, staff affiliation, doctor/caregiver category and current device fingerprints. Ordinary membership or a profile form does not grant credential authority. Only the named professional submits; only the named facility approves/rejects/suspends. Decision history is atomic and immutable. Rejected requests may be resubmitted; suspension is terminal.
- An active facility-approved doctor explicitly reviews and approves one saved referral version. The authenticated server receipt binds doctor/key, facility, current credential event and the content digest. The digest covers the selected version's facts, patient snapshot, source profile identity/revision and original-file references. Later edits cannot inherit approval. Doctor-scoped paths prevent another account reserving the same draft/version identifier.
- Approved HTML and print/PDF copies preserve the selected content and attribution, and clearly say that initiation/sending have not occurred. No clinical content is written into the approval metadata on the relay. Draft exports remain draft-marked.
- Confirmed receipts are retained inside the encrypted account vault and excluded from the old cloud-backup projection. The author can reopen and export a byte-matching approved copy offline. A missing server result does not erase a saved receipt; a conflicting or content-mismatched receipt is rejected. Approval creation still requires current online authority.
- For professionals with a credential scope, pending/rejected/suspended credentials and disabled/changed member, facility, scope or device approval block future direct and assignment transfers. Existing saved records remain readable. Legacy explicitly enrolled test pairs without credential scopes retain their bounded prior document-transfer behavior, but cannot approve referrals.

## Findings resolved during verification

An early rules test helper incorrectly expected `withSecurityRulesDisabled` to return its callback value; this caused a fresh creation timestamp on update and correctly failed the immutable-field rule. The helper now captures the snapshot explicitly. No rule was weakened to permit that update. Repeated member lookups were reduced to keep valid scoped transfer evaluations within the emulator's expression limit; the final run contains no maximum-expression-limit failures.

The distribution checker initially treated the local `referralApprovals` storage property as evidence of a leaked pilot client. Normal record parsing must preserve that property. The check now detects the approval client/UI strings and the credential backend collection, alongside all prior pilot markers. It still rejects executable sharing/approval tools in normal distributable assets.

## Remaining boundaries and next work

Approval is currently an authenticated server receipt plus a content digest, cached for historical offline reading. It is not yet a portable independently verifiable approval certificate. The receiving flow must verify the exact approved version and current publication/delivery authority; a prior receipt cannot bypass revocation. Partial server success with failed local caching is reported honestly and can be retried.

Organization delivery/initiation, destination selection, recipient acceptance, arrival, handoff acknowledgement and closure are not implemented by this milestone. Source-preserving clinician AI assistance and compact encrypted BLE handoff/read-back remain open. Permanent-code identity/claims remain synthetic; automatic multi-device synchronization, recovery and larger-attachment handling are incomplete. Public facility verification, production cloud deployment and physical NFC success are not claimed. These prototype access rules require independent security review before broader release.

The assistant owns all developer checks. The user will receive the complete core for usability review after the authorized end-to-end journey works; no technical checklist is assigned to them here.
