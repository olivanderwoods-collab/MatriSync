# Patient identity service: review-stage local implementation

31 October 2026, after `bcab125`. This implements authoritative metadata transactions in the existing local emulator environment. It does not activate permanent-code patient loading or Mother claiming in the app, deliver clinical records, or satisfy the independent protocol-review gate.

## Implemented boundary

`scripts/identity/server.mjs` binds only `127.0.0.1:4180`. It accepts one bounded JSON POST at `/v1/command`; unexpected Host, browser Origin and browser fetch-context headers are rejected. It is deliberately absent from `dev:sharing` and both distributable builds. `pnpm dev:identity` starts the developer endpoint; the assistant owns its operation. No new dependencies were installed.

The server contacts only the fixed Auth emulator on 9099 and the Standard-edition sharing Firestore emulator on 8087 for `demo-matrisync`. There is no live-project configuration. Emulator tokens are unsigned: the service checks their local issuer/audience, provider, expiry, account existence/disabled state and revocation time, and separately requires the enrolled device's ES256 signature. This is a local trust environment, not a production authentication implementation. See [Firebase's Auth emulator guidance](https://firebase.google.com/docs/emulator-suite/connect_auth).

All operations reread the approved member and exact public device keys inside the transaction. Professionals additionally require an enabled credential scope, active approved credentials, matching approved facility/approver keys and fixed doctor/caregiver category. The legacy transport exception for professionals without credential scopes does not apply. Organization roles cannot register, claim or connect through this endpoint.

## Operations and preservation

- **Register:** reserves a canonical username and source-profile identity atomically. Professionals may register their own source patients, initially unclaimed. Mothers may register only their own `self` source, immediately owned by that account. The source-profile digest uses the existing sharing scheme. Conflicting usernames, alternative usernames for an existing source and changed verifiers fail; an exact registration retry retains the original identity. Registration does not verify the contents or existence of a local encrypted patient record; that binding remains a client-integration requirement.
- **Claim:** a code proof and approved Mother account can atomically claim an unowned identity. Competing claims produce one owner. Ownership cannot be replaced. An account already owning another registered identity cannot silently claim a second. This only writes the identity ledger: it never replaces, merges or edits a local Mother profile or its documents.
- **Connect:** a currently verified professional with a code proof receives a direct metadata grant bound to that enrolled device. There is no second Mother approval prompt. A revoked grant or different device key cannot be reinstated by presenting the code again.
- **Revoke:** the first Mother owner controls direct-grant revocation after claim; before claim, the registering source account may revoke. Source provenance is unchanged. Revocation is terminal. No existing sharing channel or facility assignment is modified by these operations.

Success includes an attributed operation receipt and `clinicalDelivery: "not-integrated"`. Replaying an identical signed request returns its original timestamped receipt with `replayed: true`; it never reexecutes a grant or makes a claim about current access. A changed request with the same request ID is denied. Future clinical integration must independently read current authority, not treat a receipt as a bearer grant.

## Candidate proof construction — independent review still required

`src/identity-proof.ts` supports only the application's existing `LOCAL-<UUID-v4>` codes, with 122 random bits generated by `crypto.randomUUID()`. Unsupported legacy/short codes are rejected without rotation. Username lookup trims surrounding whitespace and lowercases ASCII letters; the accepted namespace is 3–64 letters/digits/dot/underscore/hyphen, beginning with a letter/digit. No local username/code is rewritten. Collisions and unsupported existing names need explicit migration handling before app integration.

HKDF-SHA-256 derives a 256-bit verifier from the original code, with the canonical username and protocol identifier as salt context and `code-verifier-only` as info. Claim/connect proofs use HMAC-SHA-256 over the canonical operation, including authenticated UID, enrolled key fingerprint, operation, username, UUID request ID and timestamp. The entire command is separately signed with the existing nonextractable device ES256 key. Commands expire after two minutes of clock skew. The standard primitives are documented in [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) and [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104); their use does not establish that this composed protocol is independently reviewed.

The server stores the derived verifier, never the raw code, record key or device private key. The verifier is an authentication secret: possession enables code proofs when combined with an approved actor/device. This is not PAKE and does not protect against a compromised identity service. HKDF is not a password-stretching substitute; human-chosen short codes are outside this design. The service itself can already change metadata through its trusted local administrative adapter. Clinical recipient-key authenticity, recovery, device replacement and source-authorized encrypted delivery remain unimplemented and must be reviewed before this identity ledger is trusted by a source client.

## Storage and transaction behavior

Server-only paths are `patientIdentities/{usernameDigest}`, nested `directGrants/{uid}` and immutable `events/{requestDigest}`, plus `identitySources/{sourceProfileId}`, `identityOwners/{uid}`, `identityRequests/{requestDigest}` and `identityRateLimits/{uid}`. Existing deny-by-default rules block app-client reads, lists, creates, updates and deletes; no new client permissions were added. Stored usernames and relationship IDs are metadata, not anonymous data. Development uses only fictional accounts.

Identity, ownership/source uniqueness, grants, immutable event and request receipt commit together. Authority documents participate in the same transaction. The REST adapter recognizes both HTTP aborts and aborts embedded in a streamed `batchGet` response, rolls back and retries at most five times using Firestore's `retryTransaction` context with jitter. An ambiguous commit connection failure is not automatically replayed; an explicit retry of the same signed command can recover its durable receipt. See [Firestore transaction options](https://firebase.google.com/docs/firestore/reference/rest/v1/TransactionOptions).

Authenticated, device-verified commands are limited to 20 per account during a 60-second interval beginning with the first attempt. Wrong code attempts count; state survives service restart. Body/header/time limits bound individual HTTP requests. These are local-test controls, not a production abuse-management claim. The service logs no request bodies, bearer tokens, proofs, verifiers or clinical content and returns generic failures.

## Next integration gates

Obtain independent review of this candidate proof together with recipient-key authenticity and source fulfillment. Bind registration to the actual encrypted local record while preserving all original pairs/IDs. Implement durable source-authorized encrypted delivery without a second approval prompt, explicit pending/received states, conflict handling for existing Mother self records, reviewed recovery/device enrollment and current-grant checks on future fetch/publication. Keep ordinary offline reads intact. Until these checks exist, leave the endpoint separate and browser access disabled; do not describe the current app's synthetic code forms as authoritative.
