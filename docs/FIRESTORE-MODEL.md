# Encrypted record connection — prototype, not deployed

Read-only inspection on 22 October 2026 confirmed the existing `(default)` database in `matrisync-c9de7` is **Standard**, Firestore Native, `asia-south1`. No new database, bucket or billing configuration was created.

The adapter uses one exact document: `recordOwners/{Firebase UID}/vaults/patients`. There are no collection queries, public profiles, role claims, facility grants or cross-account shares. It reads from the server and uses a transaction for compare-and-set writes. Local record edits do not invoke it. The production connection is disabled in code; only the loopback demo emulator can currently construct a connection. Enabling it later requires deployment/review of the rules and backup/restore conflict UX. Do not deploy these default-deny prototype rules over a live ruleset without first comparing existing collection requirements.

Required fields: version (1, immutable); kind (`patient-records`, immutable); salt (24-character base64, immutable); iv (16-character base64); ciphertext (24–700000 base64 characters); revision (UUID); generation (1–1000000000 integer, incremented by one); updatedAt (server timestamp). Ownership comes only from the path and matching Auth UID, never from UI role selection. Anonymous accounts are denied. Updates validate the complete schema and require a fresh IV/revision. Deletes, other document paths, all list queries and all Firebase Storage access are denied.

Before encryption, a strict projection copies only patient ID, name, birth date, profile history, creation and update dates. Document bytes, filenames, document metadata and photos are excluded. Encryption uses a separate AAD context from the local vault. The server cannot prove that arbitrary client-supplied ciphertext contains real encrypted patient data; rules restrict ownership and envelope shape, and cannot provide clinical validation or protect against a malicious owner corrupting their own data.

Device records use a different encrypted envelope plus separately encrypted document blobs in IndexedDB. Both writes commit in one transaction; a revision mismatch rejects stale saves. No plaintext patient/document metadata or key is persisted. The key is non-extractable and held only in application memory. AES-GCM uses fresh 96-bit IVs and account/document/revision-bound AAD. PBKDF2-HMAC-SHA256 uses 600000 iterations and a random 128-bit salt. These choices follow [Web Crypto AES-GCM guidance](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams) and [OWASP password-derived key guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Limitations: no passphrase recovery or rotation UI, encrypted backup/export UI or device migration yet. Browser eviction/clearing or device loss can remove local files permanently; the UI discloses this before setup. Encryption does not protect an unlocked browser or compromised script/OS. Local file downloads leave the vault as ordinary files after explicit user action. Uploaded PDFs are downloaded rather than executed in an app preview. File signature/type checks are not malware scanning. Account possession does not establish clinician credentials, consent or authority to publish a prescription. Those workflows remain disconnected.
