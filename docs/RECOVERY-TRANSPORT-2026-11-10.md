## Implemented connection

`tests-care/recovery-transport.ts` is a Node HTTP server factory around the existing emulator verifier. Tests explicitly bind it to `127.0.0.1:4192`; importing the factory does not start a listener. Its only route is `POST /v1/recovery` with exact `{action,input}` fields and actions `request`, `approve`, `close`, `reconcile`, `inspect`. No initialization, enrollment, fixture provisioning, file upload, grant change, relay or generic database action is exposed. The original signature/proof and immutable-operation contract remains unchanged.

The transport requires a loopback peer, exact Host `127.0.0.1:4192`, exact Origin `http://127.0.0.1:4192`, same-origin Fetch Metadata when supplied, JSON content type, explicit `X-MatriSync-Recovery: 1` and a bounded Bearer token. Cookies and encoded bodies are refused. Bodies are capped at 48 KiB, individual command input at 32 KiB, tokens at 8 KiB. Streaming bodies are counted even without Content-Length. There are request/header timeouts and an eight-active-request cap. There is no CORS/preflight allowance, and responses are non-cacheable with generic errors. Tokens, keys, body content and internal errors are not logged.

The server delegates identity to the actual demo Auth lookup rather than trusting a separate body UID or role. Cryptographic request UIDs must still match that account. Emulator owner credentials and the aggregate-encryption custody key stay in the server/test process. The key is supplied to the verifier, not generated or persisted by the HTTP layer. Tests use one disposable server key across multiple synthetic accounts and demonstrate account isolation and reconnecting the verifier with the same retained key. This is not production custody or a tested server-process restart with durable key recovery.

`tests-care/recovery-remote.ts` exposes a browser-safe client that accepts an asynchronous token provider, restricts execution to the fixture's exact origin and uses a fixed loopback endpoint. It copies the command before awaiting a refreshed token, omits cookies, refuses redirects, sets a timeout, validates the response envelope and never automatically retries a network failure. `reconcile` distinguishes a known pending operation (`null` from the server, returned as `undefined`) from an unavailable/denied operation. A generic failure instructs explicit reconciliation of the same operation. The client trusts the dedicated server's operation-result schema; the downstream cryptographic import/export checks remain necessary.

The browser entry exports the client, not the server. The existing browser build guard now explicitly blocks `recovery-transport` as well as the verifier/emulator/SQLite/worker modules and Node builtins. A negative import test proves it fails even for an unused server import. Public app dependencies and built assets remain separate.

## Current authority inspection

`EmulatorRecoveryBoundary.inspect(token,id)` reads an already-approved operation, its original device, current facility/staff status and each approved case assignment in one Firestore transaction. It normalizes public key representation, validates the fingerprint and requires the original device identity to remain unchanged. The result contains only the account, decision and currently allowed authority snapshot. Pending/closed/unknown/foreign operations, revoked scope and changed devices are refused. No private challenge nonce or original approval proof is exposed by inspection.

Inspection is a **point-in-time snapshot**, not an authorization lease, grant or cross-browser atomic permission guarantee. The HTTP integration refreshes it before operations, clears a previous snapshot before attempting a refresh, and refuses completion after a failed refresh. A permission change after the snapshot but before a browser commit remains an unresolved distributed boundary; do not describe this as atomic server authorization of browser export/import. Historical reconciliation continues to return the saved decision after revocation, without asserting current access.

Auth emulator tokens remain unsigned; their claim checks plus real account lookup are not production cryptographic login verification. Auth disable/revocation is still not atomic with Firestore. The exact origin and loopback checks do not solve production identity or protect against a compromised local process/origin. No public service should use this harness.
